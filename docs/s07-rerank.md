# s07-rerank: semantic07 + Qwen3 Reranker 8B

2026-11-13. Кандидат по запросу пользователя. Основа — точный
`dist/energytool-unified-v1-hybrid-semantic07.zip` (61.019, sha256 `4d1b307e…`).
Гибридный поиск (BM25 + bge-m3, `M_DENSE_MISMATCH` 0.7, `W_DENSE` 3) возвращает прежний пул из
36 разделов. Реранкер ставит в начало 12 самых релевантных из них, остальные 24 сохраняют
гибридный порядок. На платформу не отправлялся, балла нет.

Архив: `dist/energytool-s07-rerank.zip`, sha256 `51a355ebdd32d83287ac4632b6734bec404dc609428d784431b0b32add10144b`,
рядом manifest. Сборка: `python3 tools/build_s07_rerank.py` (сверяет хеш semantic07, отказывается
перезаписывать).

## Что изменено

Меняются только `solution.py` (пять точечных замен) и `config.py` (новые настройки), добавлен
`rerank.py`. `retrieval.py`, `hybrid.py`, `context.py`, `batch_io.py`, промпт, генерация, бюджет
времени и CSV побайтно как в semantic07. Это проверяют тесты.

1. Запрос `POST {LLM_BASE_URL}/rerank` в формате образца организаторов:
   `{model, query, documents, top_n: 12}`. Ключ и адрес — те же, что у генерации.
   - Модель берётся из `RERANKER_MODEL`, по умолчанию `qwen/qwen3-reranker-8b` (как в `sample_submission`).
   - Запрос — `retrieval.query(question)`, тот же, что для эмбеддингов: последняя реплика клиента и три предыдущие.
   - Документ — заголовок + текст раздела, как для эмбеддингов. Для реранкера текст обрезается до
     6000 символов (самый длинный раздел базы — 4914), в контекст модели идёт полный текст.
2. Ответ проверяется строго: индексы целые, в диапазоне, без повторов. При наличии оценок
   порядок задаёт `relevance_score`. Если пришло меньше 12, свободные места заполняются в
   гибридном порядке.
3. **Обязательные ограничения сохраняются.** Реранкер по смыслу опускает разделы «Что мы не
   делаем», «Чего утверждать нельзя», «Важное ограничение по применению». Без защиты на demo
   из контекста пропадал один такой раздел в 6 вопросах из 18 (5, 6, 7, 9, 12, 16).
   - Каждый раздел ограничений и условий из контекста semantic07 (тот же признак по заголовку,
     что в `context.select_sources`) ставится сразу за 12 выбранными. Там его берёт прежнее
     дополнение context.py: до 2 разделов ограничений сверх TOP_K.
   - Если дополнение его не взяло, он занимает место самого слабого выбора реранкера внутри
     первых 12. Размер контекста остаётся как у semantic07.
   - Итог на demo: потеряно 0 разделов ограничений из контекста semantic07, выбор реранкера
     уступил место в 7 вопросах (по одному разделу).
4. `context.pack_context` получает переупорядоченный пул и работает без изменений: первые 3,
   ограничения, остальные из 12, дополнение из всего пула.

## Резерв без реранкера

- `ET_USE_RERANKER=0` — точно semantic07: тот же запрос к модели (сквозная проверка на 18 demo).
- Любая ошибка (HTTP, таймаут, неверный ответ) — гибридный порядок semantic07 для этого вопроса.
  - Таймаут запроса 15 с, без повтора. Один повтор только после 408/429/5xx.
  - 404/405/401/403 — реранкер выключается до конца запуска сразу; любые другие сбои — после
    3 подряд. Успешный ответ медленнее 12 с тоже считается плохим, хотя результат используется.
  - Если до конца бюджета меньше 60 с, этап пропускается.
- В stderr: `rerank_ready` (первый успех), `rerank_fallback`, `rerank_disabled` — без тел запросов и ключей.

Настройки (`ET_<ИМЯ>`): `USE_RERANKER` 1, `RERANK_KEEP` 12, `RERANK_DOC_CHARS` 6000, `RERANK_TIMEOUT` 15,
`RERANK_ATTEMPTS` 2, `RERANK_RESERVE` 60, `RERANK_MAX_BAD` 3, `RERANK_SLOW` 12.
Переменная платформы `RERANKER_TOP_N` проверяется, как в semantic07, но число выбранных разделов не задаёт: оно фиксировано (12).

## Проверки без модели

  сохранение ограничений. Запрос к модели совпадает с semantic07 при выключенном реранкере,
  при 503/404/неверном ответе, при выбранных разделах контекст начинается с выбора реранкера.
- Весь набор: 267 тестов (`python3 -B -m unittest discover -s tests`), все проходят, ни один не пропущен.
- `python3 tools/check_s07_rerank.py` — оба архива как на платформе (родитель + рабочий процесс),
  18 вопросов demo, поддельный HTTP-сервис.

## Сравнение на стенде (demo, 18 вопросов организаторов)

Использованы только `demo_questions.csv` и эталоны `demo_output.csv`.

**Стенд.**
- Генерация: Qwen3-4B-Q4_K_M (заменитель Qwen3.8-27B), T=0, 700 токенов, 1 поток,
  `tools/local_eval.py run --set demo --parts 2`.
- Эмбеддинги: реальные bge-m3 Q8_0 без округления (кеш соседнего окна, одинаковый для обоих прогонов).

**Реранкер — заменитель.** Qwen3-Reranker-8B Q4_K_M (4,68 ГБ) на этой машине (M3, 8 ГБ) не работает:
- на Metal — ошибки нехватки памяти GPU и при 37, и при 23, и при 16 слоях;
- на CPU — около 35 с на каждый раздел независимо от длины (веса подкачиваются с диска),
  то есть 6–9 часов на 18 вопросов.

Поэтому локальные оценки получены от Qwen3-Reranker-4B Q4_K_M (sha256 `70996092…`): тот же шаблон
rerank, та же инструкция, `cls.output` yes/no. Код кандидата на платформе обращается к 8B.
Ответы 4B на 18 запросов (пул 36 разделов, ~25,7 тыс. символов) сохранены и отдаются прокси
`tools/rerank_stand.py serve` из кеша. Запрос к /rerank в прогоне совпал с сохранённым во всех 18 случаях (статус ok).

**Прогоны:** `work/eval/s07-demo` (архив semantic07 без изменений), `work/eval/s07-rerank-demo`
(этот архив, sha256 `51a355eb…`). Оба 18/18, returncode 0, заглушек нет, по 18 вызовов генерации.

### Источники

- Контекст изменился во всех 18 вопросах. В среднем общих разделов 9,3 из ~13,3.
- Первый раздел совпал в 10 из 18, в первой тройке в среднем 2 общих раздела.
- Разделов ограничений столько же, сколько у semantic07, во всех вопросах; размер контекста
  12–14 разделов, как у semantic07. Средняя длина контекста 9563 символа против 10076.
- Чаще всего реранкер (4B) поднимает общие разделы:
  - навигацию портфеля (`20-portfolio`: «Навигация по типу компании», «Быстрая навигация по задаче»);
  - вводные разделы продукта и «С чего начать».
  Конкретные разделы при этом опускаются: например, в 15 «Для платформы учёта» заменён на «С чего начать» и «С чего начинается разговор».
- В 18 в первую тройку попал «Сколько это стоит» чужого продукта (`25-meter-reading`) при вопросе о платформе учёта.
- Подробный отчёт по каждому вопросу: `work/rerank/report.md` (вопрос, эталон, оба ответа, источники).

\* Во время вопросов 5 и 6 кандидата машина замедлилась: свободной памяти около 15%,
разбор запроса упал с 110–240 до 30–38 токенов/с (журнал llama-server). Запросы дольше 90 с
semantic07 повторяет сам, отсюда 177 и 143 с. К реранкеру это не относится: его ответы шли из кеша.
Два BrokenPipe в журнале прокси — это те же два повтора: клиент закрыл соединение раньше ответа.
Повтор шлёт тот же запрос, и при T=0 ответ тот же. Детерминированность стенда подтвердило соседнее
окно: в прогоне `work/eval/s07-colloq08-demo` в 13 вопросах с тем же запросом ответы побайтно
совпали с `s07-demo`. Значит, разница ответов в сравнении вызвана изменением контекста, а не шумом.

Сам реранкер на стенде: 4B на Metal — 77,3 с на вопрос в среднем (51–110 с), 1391 с на 18.
Для платформы это не оценка: там 8B на серверном GPU, задержка неизвестна. При задержке больше
15 с этап выключится после 3 запросов, и запуск продолжится как semantic07.

### Ответы

**Как оценивали.**
- Слепая попарная оценка, `tools/blind_pack.py --seed 20261113`: буквы A/B перемешаны по вопросам.
- Судья — отдельный агент без доступа к ключу. Шкала платформы (A++/A+/=/B+/B++) относительно
  эталона `demo_output.csv`, спорные факты сверялись с базой.
- Файлы: `work/rerank/blind/` (answers, key, grades).

| | s07-rerank против semantic07 |
|---|---|
| Победы / ничьи / поражения | 6 / 7 / 5 |
| Значительно лучше / значительно хуже | 1 (5) / 3 (3, 11, 14) |
| Аналог Match Rate (0,5 = паритет) | 0,486 |
| Критические ошибки (вывод против эталона или выдумка) | 3 (3, 11, 14) против 1 (5) у semantic07 |
| Совпадающих ответов | 0 из 18 |
| Средняя длина ответа | 39,5 слова против 41,8 |

Критические случаи (проверены по ответам вручную):

| Вопрос | Ошибка | Связь с источниками |
|---|---|---|
| 3, кандидат | «мощность до 150 кВт допускается для юрлиц и ИП»: лимит микрогенерации подставлен к вопросу о поэтапном расширении | явной нет: оба контекста по `23-solar` |
| 11, кандидат | выдуман «трёхфазный прибор при мощности выше 15 кВт», вставлен шаблон «разложим рост на составляющие» | вероятна: ушёл раздел порогов «Главное про единицы измерения», пришли общие «Следующий шаг» и «Для первичного понимания задачи» |
| 14, кандидат | «сетевая станция с накопителями» вместо разделения сетевой и гибридной, прямого ответа нет | вероятна: из первой тройки ушёл FAQ «Если пропадёт электричество…», пришёл «Автономные и изолированные объекты» |
| 5, semantic07 | выдумана рекомендация ставить SIM-карты МТС | у кандидата ответ верный |

Где кандидат лучше:
- 5 — без выдумки про SIM;
- 2, 7, 18 — немного лучше;
- 16 — ближе к эталону по выгрузкам;
- 17 — учёл названную клиентом четвёртую категорию.

**Вывод по demo.** Улучшения не видно: попарно паритет (6–5), аналог Match Rate 0,486,
критических ошибок на 2 больше. По правилу из docs/plan.md разница в 1–2 сценария
решением не считается. Направление при этом не положительное, и найден механизм риска:
реранкер (4B) выбирает общие обзорные разделы вместо конкретных.

## Ограничения вывода

- 18 вопросов demo — настроечные данные. Генератор Qwen3-4B вместо 27B, реранкер 4B вместо 8B.
  Ранжирование 8B может отличаться.
- Балл платформы этим не предсказывается. Прошлый урок (docs/plan.md): разница в 1–2 сценария решением не считается.
- Docker и платформенный прокси (наличие `/rerank` и имени модели) не проверены.
- Прежний эксперимент с реранкером (context-rerank-review-v1, 49.829) шёл вместе с редактором
  ответа и на другой основе. Вклад реранкера там не выделен.
