## 1. Контракт и упаковка — выполнено локально
- Отклонять вход с повторяющимися ID, проверять уникальность выходных ID. Не объединять задания и не придумывать новые ID.
- Ограничение ответа 10 000 символов: проверка и управляемая обработка превышения; обычный ответ до 150 слов. Не обрезать произвольно смысл или оговорки.
- Требовать имя генеративной модели из окружения; использовать единый прокси и ключ для всех моделей. Личный API-ключ пользователя не нужен.
- Читать/валидировать параметры генерации. Поддержанные настройки поиска описывать явно.
- ZIP только solution.py, batch_io.py, requirements.txt и необходимые будущие корневые .py. README остается документацией проекта. Индексы, данные, конфигурации и .whl исключить.
- Проверять размер архива до 128 МБ. Эмулятор платформы переносит только разрешенные файлы.
Готово: граничные тесты дублей, длины 9999/10000/10001, CSV и ограниченного состава файлов проходят; пересобран ZIP. API-вызовы организаторам на этом этапе не нужны.

## 2. Довести локальный поиск
- Разделы/подразделы с сохранением контекста заголовков, таблиц и оговорок; обработка длинных фрагментов без пропуска полезного содержимого.
- Разделить последний вопрос и историю, сохранить релевантные факты; не давать устаревшей теме подавлять текущий вопрос.
- На 18 демовопросах вручную разметить необходимые факты/источники и измерять покрытие top-k. Добавить перефразировки, смену темы, неизвестный ответ, корректировки клиента.
- Эталонные ответы используются только для проверки, не включаются в поиск или промпт как готовые ответы.
Готово: отчет с найденными источниками, покрытием и объяснением промахов. Ни один результат этого этапа не называется оценкой LLM-судьи.

## 3. Контроль времени — реализован и проверен локально
- Бюджет на весь запуск, включая чтение, индексацию, генерацию и запись. Внутреннюю границу завершения задать с запасом, например 18 минут; это инженерная настройка, не требование регламента.
- Ограничить таймауты/повторы по оставшемуся времени, сдержанная параллельность. Не приравнивать 8 CPU к квоте API.
- Сохранять прогресс атомарно, обеспечивать все ID; технические сообщения не считать полноценными ответами.
- Учесть, что отмена future не останавливает выполняющийся HTTP-запрос; завершение worker-пула не должно выходить за общий бюджет.
- Тестировать медленные ответы, 429/5xx и таймауты локально на синтетическом адаптере; не обращаться к реальному API без необходимости.
Готово: воспроизводимые тесты дедлайна/ошибок, итоговый CSV и честная статистика успешных/неуспешных ответов.

## 4. Первый сабмит на платформу
После пунктов 1–3 собрать воспроизводимый ZIP. Платформа сама предоставит доступ к модели: отсутствие личного ключа не блокирует отправку. Проверить формат, запуск, полный набор ответов и результат платформы. При 401 сообщить организаторам, ключ самостоятельно не менять.
Вести журнал: версия/хеш, время МСК, изменение, статус, оценка, ошибка. 5 попыток в день; сброс в 00:00 МСК. Сейчас никакие сабмиты не отправлены.
Готово: фактический результат платформы записан. Балл >0 — только часть условий допуска; веб-чат и материалы нужны позже.

## 5. Улучшения по измерениям
Сравнивать словарный поиск с гибридным. При добавлении bge-m3 вычислять эмбеддинги базы один раз внутри запуска; не упаковывать индекс. Реранкер необязателен: включать, если улучшает качество и укладывается в бюджет. Не тратить вызов проверки модели на каждый ответ без доказанной пользы.
Контролировать факты, оговорки, краткость и полезный следующий шаг. Не оптимизироваться только под 18 демовопросов или public-набор: итог автоматической проверки private.
Score=0.7*MatchRate+0.3*WinRate; это сравнение с baseline, а не процент буквальных совпадений с эталоном.
