# Проверка решений по условиям клиента

`decision-v1/questions.csv` — 20 вопросов, 10 пар. Только этот файл передаётся решению как вход. `cases.json` — критерии и ссылки на Knowledge-base только для оценивания, никогда для поиска или генерации. Набор локальный, производный от закрытых материалов; не публиковать и не включать в конкурсный ZIP.

Пары P01–P09 проверяют изменение решения при изменении существенного обстоятельства. P03 меняет профиль клиента как единое обстоятельство (тип организации вместе с объектом анализа). P10 — контроль устойчивости: правильный вывод должен сохраниться при ошибке прежнего ассистента. Не требуем различного текста во всех парах.

## Что считается использованным

- Все эти вопросы видны разработчику: `development_visible`, не holdout.
- demo 1–18 и retrieval 1–18/p1–p8 уже использовались для настройки; не называть их независимым контролем.
- Статус `not_run` в неизменяемом cases.json — состояние при создании. Текущее использование и оценки — в docs/test-scores.md, получаемые из записей прогонов.
- Экспорт, проверка формата и синтетический тест не являются генерацией. Получение ответа и его оценивание отмечаются отдельно.
- При изменении вопросов/критериев создать decision-v2; не исправлять существующий набор после получения ответов.

## Первый эксперимент

1. Запустить точный сохранённый context-v1 на questions.csv с разрешённой моделью и базой. Сохранить ответы, фактический контекст, модель и несекретные настройки. Не подменять baseline текущим submission/solution.py: там уже hierarchy-v1.
2. В следующих вариантах сохранять тот же контекст: сначала изменить только инструкцию, затем отдельно проверить дополнительный этап. Пока эти варианты не реализованы.
3. Зарегистрировать полный CSV ответов (id,answer):

```powershell
python tools/decision_evaluation.py register --answers work/answers.csv --variant context-v1 --artifact dist/energytool-context-v1.zip --run-id context-decision-001
```

Каждый запуск — новый run-id; повтор не перезаписывает прошлый. Команда сохраняет ответы и хеши набора, архива и ответов в `work/decision-evaluation/<run-id>.json`. Этот каталог — часть локального журнала: сохранять резервную копию вместе с проектом. Он не включается в Git. Не помещать ключи в записи. Регистрация означает, что это действительно ответы модели; для имитаций использовать отдельный временный каталог, не рабочий журнал.

4. Проверить ответы по смыслу и базе, заполнить reviewer и поля scores в JSON. Каждый критерий 0 или 1, null = ещё не проверено:
   - decision: вывод соответствует required_decision;
   - conditions: сохранены решающие условия/границы, неизвестное не превращено в да/нет;
   - grounded: нет утверждений, противоречащих или не подтверждённых базой;
   - useful_action: ответ на последнюю реплику, нет повторного запроса известных данных; уточнение только по делу. Отсутствие вопроса само по себе не ошибка.
5. critical_error = true при ложном разрешении/запрете, подмене продукта, гарантии без оснований или следовании ошибке ассистента. В notes указать конкретное утверждение и источник. evidence_in_context = true/false только после проверки фактически отправленного контекста, иначе null. Можно дополнить latency_seconds и api_calls, если измерены.
6. Выполнить `python tools/decision_evaluation.py report`. Сводка — docs/test-scores.md. Важны доля правильных решений, критические ошибки и полностью правильные пары; сумма 0–4 — вспомогательная локальная оценка, не прогноз лидерборда. Частично оценённые прогоны не сравнивать с полными.

Качество не оценивается совпадением ключевых слов. На первом этапе допустима ручная оценка с именем проверяющего; для сравнения вариантов желательно скрывать их названия от проверяющего. Сценарии, использованные для исправлений, остаются диагностическими. Для независимого контроля позже нужен новый замороженный набор.

## holdout-v2 (2026-11-12)

`holdout-v2/questions.csv` и `cases.json` — 36 сценариев, составлены отдельным агентом только по Knowledge-base, без доступа к коду, документации и прошлым ответам. Набор нацелен на четыре класса критических ошибок генерации; в `cases.json` добавлены поля `error_class` и `mirror`:

- `number_vs_threshold` — вывод зависит от сравнения числа клиента с порогом или диапазоном;
- `cross_product_transfer` — цена, срок или свойство известны только для другого продукта или конфигурации;
- `assistant_error` — диалог, где клиент опирается на реплику прежнего ассистента;
- `no_information` — запрошенных сведений в базе нет;
- `control` — 16 обычных сценариев на регрессии.

В каждом целевом классе три «ловушки» и два «зеркальных» сценария (`mirror: true`): ситуация похожа, но правильное поведение противоположное — уверенное «да», подтверждение верной реплики ассистента, ответ по существу. Зеркальные ловят перекорректировку.

Запуск и разметка:

```bash
python3 tools/local_eval.py run --name <прогон> --solution <архив.zip> --set holdout2 --parts 2
python3 tools/blind_pack.py --set holdout2 --systems <прогон-1> <прогон-2> --out work/eval/<каталог>
# независимый проверяющий по judge-brief.md пишет grades.json
python3 tools/judge_report.py work/eval/<каталог> --baseline <прогон-1> --cases tests/evaluation/holdout-v2/cases.json
```

`--parts` делит набор на несколько независимых запусков: на локальной модели 36 вопросов не укладываются в 18-минутный бюджет одного запуска.

Статус: использован 2026-11-12 для выбора между тремя вариантами checks-v1 и unified-v1 (docs/checks-v1.md). Для следующего подбора не годится; набор производный от закрытой базы — не публиковать и не включать в ZIP.

## holdout-v3 (2026-11-12) — использован

`holdout-v3/questions.csv` и `cases.json` — 36 сценариев (id `W01`…`W36`), составлены отдельным агентом только по Knowledge-base, после того как holdout-v2 был использован. Формат тот же, что в holdout-v2. Пять целевых классов по два «ловушки» и два «зеркальных» сценария: к четырём классам holdout-v2 добавлен `false_conclusion` (все сведения в базе есть, но вывод легко исказить: вероятное выдать за установленное, обязательное — за добровольное, условное — за категоричное), плюс 16 контрольных. В пяти диалогах число названо в ранней реплике, а последний вопрос о другом — проверка, что ответ остаётся по теме последней реплики.

Разработчик содержание набора не читал: проверены только структура, счётчики и наличие всех 116 цитат в базе. До финальной проверки следующего кандидата не открывать вопросы, эталоны и ответы на них; использовать один раз, вместе с базовой версией в одной сессии слепой разметки (`--set holdout3`).

Статус: использован 2026-11-12 один раз — проверка сверки чисел последней реплики против hybrid и сверки по всему диалогу (docs/checks-v1.md, «Проверка 3»). После этого разработчик читал вопросы и разметку для разбора ошибок. Для следующего подбора не годится; нужен holdout-v4.

## grounded-holdout-v1 (2026-11-12)

`grounded-holdout-v1/questions.csv` и `cases.json` — 36 сценариев (id `Y01`…`Y36`), составлены отдельным агентом только по Knowledge-base, без доступа к коду, документации и прежним наборам. Формат полей — как в holdout-v3. Набор нацелен на три типа ошибок итерации grounded-v1 (docs/grounded-v1.md):

- `cross_product_transfer` — 5 ловушек и 3 зеркальных: цена, срок или свойство известны только для другого продукта или конфигурации;
- `no_information` — 5 ловушек и 3 зеркальных: запрошенных сведений в базе нет (в трёх ловушках тема и продукт в базе есть, нет именно запрошенного атрибута); в зеркальных вопрос только похож на «не по адресу»;
- `clear_answer` — 6 сценариев, все `mirror: true`: база отвечает однозначно, правильный ответ — прямой и уверенный, лишние оговорки и отказ считаются ошибкой;
- `ambiguous` — 4 сценария: вывод зависит от обстоятельства, которое клиент не назвал; правильно назвать развилку и задать один уточняющий вопрос либо предложить специалиста;
- `control` — 10 обычных сценариев.

13 диалогов; в трёх прежняя реплика ассистента верна, в двух содержит ошибку. Запуск: `python3 tools/local_eval.py run --name <прогон> --solution <архив.zip> --set grounded1 --parts 2`, разметка — `tools/blind_pack.py --set grounded1 …` и `tools/judge_report.py … --cases tests/evaluation/grounded-holdout-v1/cases.json`.

Использовать один раз, вместе с базовой версией в одной сессии слепой разметки. Набор производный от закрытой базы — не публиковать и не включать в ZIP. Статус записан в docs/grounded-v1.md.
