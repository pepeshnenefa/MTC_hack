# Проверка решений по условиям клиента

`decision-v1/questions.csv` — 20 вопросов, 10 пар. Только этот файл передаётся решению как вход. `cases.json` — критерии и ссылки на Knowledge-base только для оценивания, никогда для поиска или генерации. Набор локальный, производный от закрытых материалов; не публиковать и не включать в конкурсный ZIP.

Пары P01–P09 проверяют изменение решения при изменении существенного обстоятельства. P03 меняет профиль клиента как единое обстоятельство (тип организации вместе с объектом анализа). P10 — контроль устойчивости: правильный вывод должен сохраниться при ошибке прежнего ассистента. Не требуем различного текста во всех парах.

## Что считается использованным

- Все эти вопросы видны разработчику: `development_visible`, не holdout.
- demo 1–18 и retrieval 1–18/p1–p8 уже использовались для настройки; не называть их независимым контролем.
- Статус `not_run` в неизменяемом cases.json — состояние при создании. Текущее использование и оценки — в docs/test-scores.md, получаемые из записей прогонов.
- Экспорт, проверка формата и синтетический тест не являются генерацией. Получение ответа и его оценивание отмечаются отдельно.
- При изменении вопросов/критериев создать decision-v2; не исправлять существующий набор после получения ответов.

## Первый эксперимент

1. Запустить точный сохранённый context-v1 на questions.csv с разрешённой моделью и базой. Сохранить ответы, фактический контекст, модель и несекретные настройки. Не подменять baseline текущим submission/solution.py: там уже hierarchy-v1.
2. В следующих вариантах сохранять тот же контекст: сначала изменить только инструкцию, затем отдельно проверить дополнительный этап. Пока эти варианты не реализованы.
3. Зарегистрировать полный CSV ответов (id,answer):

```powershell
python tools/decision_evaluation.py register --answers work/answers.csv --variant context-v1 --artifact dist/energytool-context-v1.zip --run-id context-decision-001
```

Каждый запуск — новый run-id; повтор не перезаписывает прошлый. Команда сохраняет ответы и хеши набора, архива и ответов в `work/decision-evaluation/<run-id>.json`. Этот каталог — часть локального журнала: сохранять резервную копию вместе с проектом. Он не включается в Git. Не помещать ключи в записи. Регистрация означает, что это действительно ответы модели; для имитаций использовать отдельный временный каталог, не рабочий журнал.

4. Проверить ответы по смыслу и базе, заполнить reviewer и поля scores в JSON. Каждый критерий 0 или 1, null = ещё не проверено:
   - decision: вывод соответствует required_decision;
   - conditions: сохранены решающие условия/границы, неизвестное не превращено в да/нет;
   - grounded: нет утверждений, противоречащих или не подтверждённых базой;
   - useful_action: ответ на последнюю реплику, нет повторного запроса известных данных; уточнение только по делу. Отсутствие вопроса само по себе не ошибка.
5. critical_error = true при ложном разрешении/запрете, подмене продукта, гарантии без оснований или следовании ошибке ассистента. В notes указать конкретное утверждение и источник. evidence_in_context = true/false только после проверки фактически отправленного контекста, иначе null. Можно дополнить latency_seconds и api_calls, если измерены.
6. Выполнить `python tools/decision_evaluation.py report`. Сводка — docs/test-scores.md. Важны доля правильных решений, критические ошибки и полностью правильные пары; сумма 0–4 — вспомогательная локальная оценка, не прогноз лидерборда. Частично оценённые прогоны не сравнивать с полными.

Качество не оценивается совпадением ключевых слов. На первом этапе допустима ручная оценка с именем проверяющего; для сравнения вариантов желательно скрывать их названия от проверяющего. Сценарии, использованные для исправлений, остаются диагностическими. Для независимого контроля позже нужен новый замороженный набор.
